# Личные аккаунты и заказы: внутренние сервисы v2

Эти модули готовы для HTTP-интеграции по docs/PLATFORM_V2_PROPOSAL.md. По новому решению пользователя API и функциональные страницы ведёт второй Codex, а первый — только дизайн; ждать согласования серверных схем дизайнером больше не требуется. Модули **не подключены к server.mjs**, не создают новые доступные HTTP endpoints и не меняют работающий demo API v1. npm start продолжает запускать прежнее приложение. Наличие сервисных тестов не означает готовность новых трёх страниц.

## Состав

- store.mjs: отдельная приватная JSON-база schemaVersion=2, сериализованные атомарные записи, копии входного состояния и выходов. Один серверный процесс. Базу v1 отвергает без перезаписи.
- auth.mjs: серверный Google authorization-code flow с PKCE, browser-bound одноразовый state, проверка Google userinfo, аккаунт по sub, сессии с непрозрачными токенами и logout. Пароли не собираются. Нет ключей — begin/callback возвращают сервисную ошибку 503.
- profile.mjs: собственный профиль, публичная проекция без контактов/email/Google subject, редактирование с проверкой версии, сохранение информации двух ролей. Портфолио первого шага — ссылки, не автоматически подтверждённые кейсы.
- orders.mjs: самостоятельные отклики личного пользователя, категории, собственная история, ручной выбор исполнителей и рабочие статусы. Владелец и текущая роль проверяются из сохранённого состояния внутри очереди.
- files.mjs: PDF/UTF-8 TXT, 5 МиБ/файл, 3 файла/заказ, 20 МиБ/аккаунт. Метаданные отдельно от приватного base64. Загрузка и удаление меняют версию; ответ загрузки содержит версию именно своей операции. Доступ после начала работы остаётся владельцу и выбранным исполнителям.
- reviews.mjs: отдельный публичный текст отзыва после принятого результата, без копирования приватного evidence. Статус выполненной работы не означает подтверждённую оплату.

Функции принимают userId только от доверенного будущего HTTP-адаптера. Передавать туда userId/role из тела запроса вместо проверенной сессии нельзя. Внутренние методы не являются самостоятельной границей аутентификации.

## Обязательная HTTP-интеграция следующим шагом

1. Второму Codex зафиксировать формы запросов/ответов и переходы в общем API_CONTRACT вместе с HTTP-реализацией и опубликовать их для шаблонов первого. Ниже перечислены требования адаптера, а не уже реализованные HTTP-защиты.
2. Создать platform store вне public/ и вне demo DATA_FILE. Он содержит персональные данные, хеши сессий и файлы, не должен попадать в статическую раздачу или Git. Не использовать две store-инстанции одновременно для записи в один файл. Для многопроцессного сервера нужна транзакционная БД.
3. Подключить Google конфигурацию только на сервере: Client ID, Client Secret, фиксированный redirect URI. Вход запрашивает только openid/email/profile, без доступа к Google Drive или Gmail; offline/refresh tokens не используются. Редирект после входа остаётся внутри приложения.
4. begin.stateCookie и callback.sessionToken передаются только cookie HttpOnly; SameSite=Lax, Path=/; Secure на HTTPS. Локальный HTTP разрешён только loopback. State cookie очищается после любого завершения callback. Session token никогда не включается в JSON/логи. Выход отзывает запись и очищает cookie.
5. На мутации проверять доверенный Origin и CSRF-токен; на вход и создание данных добавить ограничения частоты. Обрабатывать OAuth-отмену без потери пользовательского черновика и без вывода кода/секрета в ошибке. Внутренний TTL state 10 минут, session 7 дней; незавершённые входы после рестарта начинаются заново.
6. Прежде чем читать большие входные файлы, проверить сессию, лимит запроса и тип. Выдавать файл attachment + nosniff с корректным кодированием имени. Не подставлять blob в JSON каталога. PDF-сигнатура и UTF-8 — проверка формата, не антивирус; реальное публичное размещение требует отдельной проверки файлов и квот.
7. Подключить экранные состояния и проверить браузером: гость → Google → возврат к заказу → solo-отклик → выбор → принятие результата → отзыв. Отдельно проверить второй аккаунт, 401, 403, 409 и отсутствие личных данных в публичном ответе.

Google Cloud пока не настроен: пользователь явно отложил этот шаг. Живых запросов к Google в проверках не было. Новый login нельзя показывать как работающий или подменять созданием фиктивного пользователя.

## Проверки

`npm test` на Node 20+. platform-*.test.mjs проверяют сервисы с временными базами и подставными ответами Google. platform-journey.test.mjs связывает вход, профиль, solo-отклик, файл, решение и принятие результата; это сервисный, не браузерный тест.

Не реализованы в этом шаге: HTTP v2, новые страницы, DOCX/фото-загрузки, состав пользовательских команд, редактор подтверждённых кейсов и AI-портфолио, личная балльная система, AI-соответствие отклика. Эти запросы пользователя сохраняются в предложениях, а не объявляются готовыми.
