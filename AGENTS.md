# Совместная работа над HackAlem

Мы делаем один MVP силами двух участников и двух независимых сессий Codex.
Работайте короткими завершёнными этапами. Не реализуйте весь проект за один заход.

## Общие договорённости

- Требования и этапы: `docs/TEAM_PLAN.md`. Форматы данных: `docs/API_CONTRACT.md`.
- По прямому решению пользователя от 23.09.2026 первый Codex отвечает только за дизайн и шаблоны. Второй Codex отвечает за сервер, AI, функционал страниц, подключение API, контракт, интеграцию и функциональные тесты.
- Общая сборка содержит рабочий API v1, внутренние сервисы v2 и Commissioner-витрину a61cc5f. После объединения 135 тестов проходят на Node 24. Для фактического подключения операций к экранам читайте актуальные STATUS-файлы; сервисный тест не означает готовый UI.
- Айдентика интерфейса — «alem / бюро практики», см. docs/BRAND_DIRECTION.md. Сохраняйте фактический язык, визуальную структуру паспорта и серверный источник рейтинга.
- Работайте от общей истории Git, в разных ветках. Не создавайте второй независимый корневой проект.
- Перед изменениями проверяйте `git status`. Не удаляйте и не перезаписывайте работу другого участника.
- Изменения API описывает и реализует второй Codex вместе с подключением экранов. Публикуйте актуальный контракт и сообщайте о затрагиваемых шаблонах через STATUS. Ожидание одобрения серверного контракта дизайнером больше не блокирует функциональную работу.
- `public/tasker/**`, дизайн-витрина `public/tasker-system.html`, визуальные спецификации и новые дизайн-шаблоны — область первого Codex. `server.mjs`, `src/**`, транспорт и функциональная логика в `public/`, функциональные тесты и интеграция страниц — второго. Не менять один файл одновременно: резервируйте конкретные пути в STATUS. Перенос утверждённых шаблонов в рабочие экраны выполняет второй Codex.
- Корневые настройки, документацию контракта и зависимости теперь координирует второй Codex для функциональной интеграции. Секреты хранятся только на сервере, в окружении или локальном исключённом из Git .env.
- После этапа сообщайте: что работает, какие файлы изменены, чем проверено, что требуется от другого участника.
- Не заявляйте о передаче сообщения другому Codex: независимые сессии координируются через Git, файлы и людей.

## Координация через GitHub

- Выполняйте `docs/COORDINATION.md`. Репозиторий: `BAITC-Hacks/hack-f0370cc6-rm-edtech`.
- Перед каждым небольшим этапом и перед интеграцией запускайте `npm run team:sync -- frontend` или `npm run team:sync -- backend` по своей роли. Это fetch и чтение статуса другой ветки, не автоматический merge.
- В начале этапа публикуйте в своём STATUS текущую задачу и занятые файлы. После законченного шага — результат, тесты, ограничения и следующий шаг. Коммитьте и отправляйте только свою ветку в рамках согласованной работы; никогда не добавляйте секреты или локальную базу.
- Проверяйте обновления также после исправления ошибки контракта, перед изменением общего API и при блокировке на другом участнике. Пока зависимость не готова, продолжайте независимую часть работы.
- Изменения другой ветки читаете через `git show`/`git diff`; перед объединением сохраняете свою работу. Изменения рабочего дерева не публикуются и не появляются у второго участника сами собой.
- После завершения активной задачи фоновое чтение GitHub не продолжается. Не обещайте постоянный мониторинг без отдельной настроенной автоматизации.

## Продуктовые инварианты

- Рейтинг 0–100 считает сервер по подтверждённым полям; AI не выставляет баллы.
- Все опубликованные задачи видны всем командам. Низкий рейтинг не запрещает отклик.
- Бизнес вручную выбирает одну, несколько или ни одной команды.
- Баллы команды начисляются за подтверждённый бизнесом результат этапа, не за отправку или принятие отклика.
- AI не добавляет неизвестные факты. Перед публикацией человек редактирует и подтверждает карточку.
- Локальную AI-заглушку явно обозначайте. Демонстрируйте промпт, вход, выход и обработку ошибок.
- Демо-переключатель ролей не является настоящей аутентификацией. Не описывайте MVP как готовый к публичной эксплуатации с реальными данными.

## Стек и проверка

Node.js 20+, ES modules, сервер на стандартных модулях Node, интерфейс HTML/CSS/JavaScript, JSON-хранилище. Исходная цель — запуск `npm start` без установки сторонних библиотек.

Новые зависимости добавляйте только при конкретной необходимости. Проверяйте изменения подходящими тестами; не тратьте время на тесты, дублирующие разметку. Для серверных тестов используйте встроенный `node:test` и временную базу. Не портите демонстрационную базу тестами.
