# Контракт интерфейса и сервера версии 1

GET /api/state, GET /api/catalog и POST /api/tasks реализованы и проверены совместно с интерфейсом. Остальные описанные ниже операции относятся к следующим этапам; их актуальная готовность отражается в BACKEND_STATUS и FRONTEND_STATUS. Форматы данных сохранены без изменения.

По актуальному решению пользователя владелец API и функционального подключения интерфейса — второй Codex; первый готовит дизайн и шаблоны. Оба используют один origin, поэтому отдельная настройка CORS не нужна. Node.js 20+, `npm start`, по умолчанию порт 3000; `PORT` и `DATA_FILE` настраиваются через окружение. Сервер раздаёт `public/`. Актуальное распределение файлов — docs/COORDINATION.md.

## Общие правила

- JSON в UTF-8. Успешные ответы: 200, при создании — 201.
- Ошибка: `{ "error": { "code": "VALIDATION_ERROR", "message": "Заполните поле…", "fields": {} } }`.
- 400 — некорректный ввод, 403 — действие не своей демонстрационной роли, 404 — объект или ещё не реализованный маршрут не найден, 405 — неподдерживаемый метод существующего endpoint, 409 — устаревшая версия, 413 — большой запрос, 500 — внутренняя ошибка без стека в ответе.
- Клиент не передаёт авторитетные баллы, confirmedFields, статусы чужих объектов и даты. Сервер формирует их сам.
- Демо-роль передаётся в JSON мутации: `role: "business", businessId: "business_demo"` либо `role: "team", teamId: "team_orbit"`. Это переключение ролей для хакатона, не аутентификация и не граница безопасности.
- Записи хранятся атомарно, мутации последовательны. Тесты используют отдельный временный DATA_FILE.
- У ссылок разрешены только абсолютные HTTP(S) URL. Неизвестные ID, типы полей и переходы отклоняются.

## Модели

### Поля карточки

`fields` — объект строк. Незаявленные сведения остаются пустыми строками. Названия ключей и длины заданы `FIELDS` в `src/domain.mjs`.

```json
{
  "title": "Прогноз спроса для кофейни",
  "context": "",
  "need": "",
  "users": "",
  "data": "",
  "constraints": "",
  "result": "",
  "success": "",
  "contact": "",
  "format": "",
  "feedback": ""
}
```

`task` содержит `id`, `businessId`, `raw`, `industry`, `company`, `initials`, `color`, `tags`, `fields`, `confirmedFields`, `confirmedAt`, `published`, `publishedAt`, `createdAt`, `updatedAt`, `version` и вычисляемый `rating`.

`rating`: `{ score, level: { key, label, description }, breakdown, missing }`.

`breakdown`: массив `{ label, max, parts: [[fieldKey, weight]], earned, missing: [{ key, label, weight }] }`.

`missing`: объединённый массив недостающих подтверждённых полей, отсортированный по потенциальному приросту баллов.

`level.key`: `draft | working | ready | priority`. `draft` — уровень 0–39, а `published: false` — статус публикации; не смешивать.

Вес: context 10, need 10, data 20, result 15, success 15, constraints 10, users 10, contact 3, format 3, feedback 4. Итого 100. title обязателен для публикации, но баллов не даёт. Это детализация рекомендованной шкалы ТЗ. Балл за поле начисляется лишь при непустой строке и явном подтверждении человеком. Оценка проверяет полноту, а не истинность утверждений. AI не подтверждает поля и не выдаёт рейтинг.

`team`: `{ id, name, initials, color, description, members, interests: [], skills: [], technologies: [], points }`. `points` вычисляется по подтверждённым этапам предложений, не принимается от клиента.

`proposal`: `{ id, taskId, teamId, idea, plan, duration, link, status, createdAt, milestones: [] }`.

`status`: `pending | accepted | rejected`.

`milestone`: `{ key: "prototype" | "result", points, evidence, confirmedAt, confirmedBy }`.

## GET /api/state

```text
{
  tasks: Task[],
  teams: Team[],
  proposals: Proposal[],
  drafts: [{ text, industry }],
  meta: { fields: FIELDS, rubric: RUBRIC, industries: string[], stages: STAGES, aiMode: "local" | "remote" }
}
```

Возвращает демонстрационное состояние, включая неопубликованные задачи для бизнеса. Это не публичный production API. У каждого task есть актуальный серверный rating. UI каталога использует GET /api/catalog, чтобы не показать неопубликованный черновик.

## GET /api/catalog

Query-параметры `industry`, `level`, `query` необязательны. Пустое значение снимает фильтр. Неизвестный параметр, повтор параметра или неизвестное значение industry/level возвращает 400. Ответ: `{ tasks: Task[] }`. Поиск query убирает крайние пробелы, не учитывает регистр и проверяет fields, company, industry и tags.

Только опубликованные задачи. Сортировка по rating.score по убыванию, при равенстве — по publishedAt по возрастанию. Фильтры не закрывают доступ к остальным задачам: пользователь может сбросить их. Не фильтровать по команде или минимальному рейтингу автоматически.

## POST /api/tasks

Вход: `{ role, businessId, raw, industry }`. raw — непустой текст до 4000 символов, industry — значение INDUSTRIES.

Выход 201: `{ task }`. Новый неопубликованный черновик с пустыми fields, confirmedFields=[], score=0, version=1. company по умолчанию — нейтральная UI-метка «Мой бизнес», а не выдуманное AI название. Создание черновика не вызывает автоматическую публикацию.

## POST /api/ai/analyze

Вход: `{ raw, industry, fields, answers }`; answers — объект `{ fieldKey: "ответ пользователя" }`, поля кроме raw/industry могут отсутствовать.

```text
{
  mode: "local" | "remote",
  fields: Fields,
  questions: [{ field: "data", question: "Какие данные доступны?", reason: "Команда сможет проверить решение" }],
  missingFields: string[],
  warnings: string[]
}
```

Не менее трёх уместных вопросов, предпочтительно по незаполненным полям. На первом проходе предлагать 3–6 вопросов. Никаких придуманных метрик, сроков, контактов или источников. Нет данных — пустая строка и вопрос. Не стирать ответы пользователя при повторном анализе. Анализ не меняет сохранённую задачу. Результат показывается в редактируемой форме.

Уточнение повторного анализа: непустой answers[field] заменяет соответствующее поле; пустой ответ не стирает существующий текст. Если fields.context отсутствует, разрешён дословный перенос raw; явно переданный пустой context остаётся пустым. При первом проходе можно передавать fields={}, при повторном — текущий отредактированный снимок. Удаление поля человек фиксирует в fields, а не пустым answers.

Внешний AI необязателен на первом этапе. При его подключении: ключ только на сервере, ограничение времени и размера, проверка JSON и схемы, локальный fallback с предупреждением. В репозитории должны быть промпт и примеры input/output. Проверять ошибку провайдера и некорректный ответ тестами. Если внешний API не настроен, mode=local и интерфейс честно сообщает о локальной заглушке.

## PUT /api/tasks/:id

Вход: `{ role, businessId, version, industry, fields, confirmed: true }`.

Сохранение полного отредактированного снимка после действия «Подтвердить сведения». Требовать confirmed === true. Сервер чистит fields, формирует confirmedFields из непустых полей, обновляет даты, увеличивает version, пересчитывает rating. Удалённое поле перестаёт давать баллы. published сохраняется; каталог отражает новый рейтинг.

Не подтверждённые правки до нажатия остаются в форме UI. Клиент может показывать предварительный расчёт с явной подписью, но официальным считается только рейтинг сервера после подтверждения.

Выход: `{ task }`. При несовпадении version — 409 с предложением перечитать задачу.

## POST /api/tasks/:id/publish

Вход: `{ role, businessId, version }`. Требуется владелец, непустое название и ранее подтверждённая текущая карточка. Не требовать полного заполнения или минимального рейтинга. Первая публикация устанавливает publishedAt; повторная не меняет порядок при равных баллах.

Выход: `{ task }`. Версия увеличивается при фактическом изменении.

## POST /api/tasks/:id/proposals

Вход: `{ role: "team", teamId, idea, plan, duration, link }`.

Любая существующая команда, любая опубликованная задача, любой рейтинг. idea/plan/duration/link непустые, HTTP(S) ссылка валидна. Не вводить лимит числа откликов и не запрещать отклик из-за наличия выбранных команд.

Выход 201: `{ proposal }` с pending и пустыми milestones. Баллы команде не начисляются.

## PATCH /api/proposals/:id

Вход: `{ role: "business", businessId, status: "accepted" | "rejected" }`.

Только владелец соответствующей задачи. Можно принять несколько разных предложений или отклонить все. Принятие одного не меняет другие автоматически. Изменение решения допустимо до первого подтверждённого этапа; после него возвращать 409 для попытки отказа. Само принятие не начисляет баллов.

Выход: `{ proposal }`.

## POST /api/proposals/:id/milestones

Вход: `{ role: "business", businessId, key: "prototype" | "result", evidence: "Что проверили и приняли" }`.

Только владелец задачи, только accepted proposal. Требовать непустое evidence. STAGES: prototype +50, result +100; итоговый этап после прототипа. Повторная отправка того же key возвращает текущее состояние без нового начисления. Переотправка не заменяет доказательство уже принятого этапа.

Выход: `{ proposal, team }` с обновлённым points.

## Дополнительные возможности

Рекомендации по навыкам и интересам допустимы после обязательного сценария. Не скрывать общий каталог. Рекомендовать только задачи с рейтингом не ниже 40; использовать заявленные навыки и интересы, не чувствительные характеристики.

Кнопка сброса демонстрации и экспорт данных — отдельные будущие улучшения, не часть обязательного первого этапа.
