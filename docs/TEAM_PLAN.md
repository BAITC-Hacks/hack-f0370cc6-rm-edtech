# План совместной разработки HackAlem

Цель — законченный и убедительный MVP по ТЗ, который можно показать за пять минут. Рабочее название — Alem Tasks. Дедлайн со слов команды: на момент обсуждения оставалось четыре часа; перед каждым этапом сверяйте реальное оставшееся время.

## Идея продукта

Представитель бизнеса описывает проблему простыми словами. Ассистент помогает заполнить пробелы. Бизнес видит, какие подтверждённые сведения повышают готовность задачи и облегчают работу студентов. Команды свободно выбирают задачи. Решение о сотрудничестве принимает бизнес.

Сильный момент демонстрации: одна и та же задача проходит путь от слабого описания к понятному предложению, получает более высокий рейтинг и поднимается в каталоге. Показываем причину каждого изменения баллов.

## Ответственность

| Участник | Решения и работа | Файлы |
| --- | --- | --- |
| Амир | Продукт, выбор визуального направления, финальная сборка, демонстрация | Принимает решения о пользовательском сценарии |
| Первый Codex | UI, каталог, конструктор, экраны откликов и результатов, интеграция с API | `public/**`, `tests/e2e/**`, корневые настройки, README, контракт |
| Брат | Проверка ТЗ, контроль серверного потока, тестирование от лица бизнеса и команды | Проверяет логику и сценарии |
| Второй Codex | HTTP API, хранение, рейтинг, AI, отклики, ручной выбор, баллы за этапы | `server.mjs`, `src/**`, `tests/backend/**`, `docs/BACKEND_STATUS.md` |

Это исходное распределение по границам кода, а не предположение об опыте участников. Если меняются владельцы, сначала меняем эту таблицу.

## Общий репозиторий

Общий репозиторий: https://github.com/BAITC-Hacks/hack-f0370cc6-rm-edtech.

Один репозиторий и одна исходная история Git с самого начала. Вторая локальная папка должна стать клоном общего репозитория. Если там уже есть работа, сначала сохранить её отдельно и переносить нужные файлы осознанно. Не создавать новую Git-историю поверх существующего репозитория. Сначала проверить его содержимое и имеющиеся инструкции, затем переносить подготовленные здесь заготовки без перезаписи чужих файлов.

На машине первого участника GitHub-аутентификация настроена, подтверждены права WRITE. Рабочая папка привязана к общей истории от f19c8d4, ветка feat/frontend. Дальнейшая координация описана в docs/COORDINATION.md. Пароли, токены и API-ключи в чат и Git не передаются.

- `main` — проверенные общие версии.
- `feat/frontend` — первый Codex.
- `feat/backend` — второй Codex.
- Ветки имеют общий стартовый коммит f19c8d4. Первая интегрированная версия подготовлена в `feat/frontend` и поступает в `main` через проверенный PR.
- Уже созданные ветки не пересоздавать: получать общие изменения через fetch и проверенное слияние.
- Небольшие PR на каждый работающий этап. Амир координирует слияние и проверяет сборку.
- Перед следующей порцией работы синхронизироваться с `main`, сохранив локальные изменения коммитом. Без force push, `reset --hard` и перезаписи чужих файлов.
- Не ждать конца хакатона, чтобы впервые запустить обе части вместе.

Пример локальных команд после проверки репозитория и публикации общего начального коммита:

```sh
# У брата: клонировать в новую свободную папку
git clone https://github.com/BAITC-Hacks/hack-f0370cc6-rm-edtech.git hackalem-team
cd hackalem-team
git switch -c feat/backend

# У Амира: в исходном репозитории
git switch -c feat/frontend
```

Синхронизация чистой рабочей ветки с общим `main`:

```sh
git fetch origin
git merge origin/main
```

Общий репозиторий уже существует. Локальная feat/frontend создана от общей истории; feat/backend создана вторым участником. Публикация веток подтверждается по origin, а не наличием локального коммита или архива.

## Этапы на оставшееся время

| Примерный интервал от старта работы | Первый Codex | Второй Codex | Проверяемый результат |
| --- | --- | --- | --- |
| 0–15 минут | Общая структура, контракт, ветка | Клон, чтение контракта, запуск заготовок | Одинаковая база и границы работы |
| 15–50 минут | Первый экран каталога, карточки, переключатель роли | Сервер, GET state/catalog, сохранение данных | Интерфейс показывает реальные серверные карточки |
| 50–115 минут | Конструктор: черновик → вопросы → редактирование → подтверждение | Создание, AI-анализ, подтверждение, публикация, рейтинг | Слабая задача становится опубликованной; рейтинг растёт |
| 115–160 минут | Форма отклика и сравнение предложений | Отклики, выбор/отказ, этапы прогресса | Сквозной сценарий завершён |
| 160–200 минут | Ошибки, пустые состояния, визуальная доработка | Проверки границ рейтинга и решений, устойчивость AI | Все обязательные условия ТЗ проверены |
| Последние 30–40 минут | README, демонстрация и репетиция | Проверка запуска из чистого клона, поддержка исправлений | Надёжная версия для защиты |

В каждом этапе сначала делаем минимальный законченный кусок и показываем человеку результат. Дальше выбираем следующее улучшение. Если времени меньше, сокращаем украшения и дополнительные возможности, оставляя сквозной сценарий и репетицию.

## Требования и баллы жюри

- Сквозной сценарий — 20: черновик, минимум три уместных вопроса, редактируемая карточка, подтверждение, публикация, отклик, ручное решение.
- Качество карточки — 15: название, контекст, потребность, пользователи, данные, ограничения, результат, критерии успеха, контакт и формат взаимодействия.
- Геймификация бизнеса — 25: рейтинг 0–100, расшифровка, недостающие сведения, пересчёт подтверждённых дополнений, влияние на сортировку.
- Каталог и отклики — 15: доступность всем командам, фильтры по теме и готовности, идея, план, срок и ссылка, ручной выбор одной/нескольких/ни одной команды.
- AI — 10: полезная структурированная функция, отсутствие выдуманных фактов, промпт и обработка некорректного ответа; при недоступности API разрешена обозначенная заглушка.
- Техническое качество — 10: запуск, валидация, структура, инструкция.
- Демонстрация — 5: целостный сценарий до пяти минут.

Минимальные синтетические данные: 5 черновиков, 5 карточек с полями и рейтингом, 5 профилей команд, 5 предложений. Текущие заготовки содержат эти наборы; их ещё нужно проверить тестами.

Уровни: 0–39 — требует уточнения, 40–69 — рабочая, 70–89 — готовая, 90–100 — приоритетная. Опубликованная задача с 0–39 баллами остаётся видимой и доступной для отклика. Неопубликованный черновик и низкий уровень готовности — разные состояния.

Баллы команды начисляются после подтверждённого бизнесом этапа. Для MVP предлагаются два этапа: проверенный прототип +50 и принятый результат +100. Эти значения — наше продуктовое решение, не веса из ТЗ. Повторное нажатие не начисляет баллы повторно.

Не планируем полноценную авторизацию, чат, календарь, обучение модели, векторную базу и большой трекер.

## Приёмка

1. Из чистого клона приложение запускается по README.
2. Пять исходных карточек отсортированы по рейтингу, фильтры работают.
3. После минимум трёх уточняющих вопросов человек редактирует и подтверждает карточку.
4. Баллы подтверждённой задачи пересчитываются по формуле, видны причины начисления.
5. Слабую задачу можно опубликовать; команда может откликнуться.
6. Изменение подтверждённых сведений меняет положение задачи в каталоге.
7. Две команды могут получить ручное одобрение одной задачи; возможен отказ всем.
8. Сам отклик и его принятие не начисляют команде баллы. Подтверждение этапа начисляет их однократно.
9. AI-ошибка не ломает конструктор; неизвестные данные остаются незаполненными.
10. После перезапуска данные сохраняются.

## Как передавать работу

После каждого этапа обновлять свой STATUS-файл и публиковать его вместе с кодом в своей ветке. Коллега читает его через `npm run team:sync`, без обязательной пересылки сообщений через человека:

```text
Ветка/коммит или PR:
Готово:
Изменённые файлы:
Проверка и результат:
Изменения контракта: нет / описание
Нужно от второго участника:
Следующий небольшой этап:
```

Независимые Codex не видят друг друга автоматически. Общий контекст передаётся через опубликованные файлы и PR по docs/COORDINATION.md. Продуктовые решения принимают Амир и брат. Это синхронизация во время активной задачи, а не постоянная фоновая работа.
