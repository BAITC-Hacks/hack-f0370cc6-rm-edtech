# Совместная работа через GitHub

Репозиторий: https://github.com/BAITC-Hacks/hack-f0370cc6-rm-edtech.

Два Codex работают параллельно на разных компьютерах. Общая память — опубликованный код, API_CONTRACT.md и два STATUS-файла. Непереданные изменения и содержимое независимых чатов не видны другому агенту.

## Ветки и владельцы

| Ветка | Владелец | Область |
| --- | --- | --- |
| feat/frontend | Первый Codex с Амиром | public/**, scripts/**, tests/e2e/**, README, корневые настройки, контракт и интеграция |
| feat/backend | Второй Codex с братом | server.mjs, src/**, tests/backend/**, docs/BACKEND_STATUS.md |
| main | Общая проверенная версия | Обновляется через проверенное слияние, без force push |

Первый серверный этап первоначально перенесён из проверенного архива брата и интегрирован с frontend. Затем получена опубликованная feat/backend до a092e66 и объединена её история, включая исходный серверный 9bcbddb. Сервер, интерфейс и тесты в архиве и опубликованной ветке совпали. Общая интеграция находится в feat/frontend, PR #1; main обновляется после проверки PR.

## Контрольная точка перед каждым этапом

Первый Codex:

```sh
npm run team:sync -- frontend
```

Второй Codex:

```sh
npm run team:sync -- backend
```

Команда получает remote refs через git fetch и читает STATUS-файл из ветки коллеги. Она не меняет рабочие файлы и не объединяет ветки. Если ветка ещё не опубликована, сообщает об этом. Для деталей используйте `git show origin/feat/backend:docs/BACKEND_STATUS.md` или соответствующий frontend-файл, а также git diff.

## Как публиковать прогресс

В начале небольшого этапа обновите свой статус текущей задачей и планируемыми файлами. После завершения напишите, что готово, чем проверено и что осталось. Опубликуйте статус вместе с кодом в своей ветке. Не используйте git add . вслепую: проверьте diff и список файлов, исключите секреты, базу и постороннюю работу.

Структура STATUS:

```text
Текущий этап:
Сейчас делаю:
Занятые файлы:
Готово:
Проверки:
Нужно от коллеги:
Следующий шаг:
```

Не ждите ручной пересылки результатов через человека. Проверяйте другую ветку перед следующим этапом и при зависимости от нового endpoint. Fetch не запускается непрерывно сам по себе; агент делает это во время активной задачи. Завершённую задачу нужно продолжить новым запуском или отдельной автоматизацией.

## Интеграция

1. Сохранить свою работу коммитом в своей ветке.
2. Выполнить fetch и изучить diff другой ветки.
3. Объединить нужные проверенные изменения без force push. Если Git показывает конфликт, понять обе версии и сохранить согласованный результат; не выбирать ours/theirs для всего репозитория автоматически.
4. Запустить npm test и сквозную проверку затронутого сценария.
5. Опубликовать интегрированный результат и обновить статус.

## Следующая согласованная пара задач

- Frontend: первый шаг конструктора — исходное описание до 4000 символов, отрасль, валидация и состояние отправки; интеграция с POST /api/tasks, когда endpoint опубликован.
- Backend: POST /api/tasks с валидацией и сохранением, затем отдельным этапом POST /api/ai/analyze. Не менять public/** и схему API без согласования.
- До настоящего ответа сервера UI не показывает успешное сохранение. AI-режим в meta пока не означает, что AI endpoint реализован.

Эта договорённость заменяет ручную пересылку архивов после первоначальной публикации обеих веток.
