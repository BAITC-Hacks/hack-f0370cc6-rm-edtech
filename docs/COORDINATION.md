# Совместная работа через GitHub

Репозиторий: https://github.com/BAITC-Hacks/hack-f0370cc6-rm-edtech.

Два Codex работают на разных компьютерах. Общая память — опубликованные ветки, API_CONTRACT и STATUS-файлы. Незакоммиченная работа и независимые чаты друг другу не видны.

## Актуальное решение пользователя от 23.09.2026

Пользователь явно поручил объединять дизайн-шаблоны первого Codex со всем backend и отправлять изменения в командный репозиторий. Первый Codex теперь отвечает **только за дизайн**. Второй Codex отвечает **за весь функционал, сервер, AI, подключение и функциональное оформление экранов**. Это заменяет прежнее правило, по которому весь public/**, API-контракт и интеграция принадлежали первому Codex.

| Ветка | Владелец | Область |
| --- | --- | --- |
| feat/frontend | Первый Codex | Дизайн, визуальная система, шаблоны, Commissioner/цвета, docs/BRAND_DIRECTION, docs/FRONTEND_README, docs/FRONTEND_STATUS |
| feat/backend | Второй Codex | Сервер, AI, API-контракт, функциональная логика страниц и форм, транспорт, тесты, интеграция шаблонов, корневые настройки, docs/BACKEND_STATUS |
| main | Общая проверенная версия | Обновляется проверенным слиянием; force push запрещён |

Дизайн-исходники public/tasker/** и витрина public/tasker-system.html остаются первым Codex. Рабочие public/app.js, api.js, index.html и функциональные страницы подключает второй. Если дизайнеру нужно править рабочий экран, сначала резервировать точные файлы в FRONTEND_STATUS; второй Codex читает это до следующего шага. Изменения шаблонов не заменяют функциональные файлы целиком: переносить осмысленно, сохраняя обработчики, состояния формы и API.

## Контрольная точка

Перед небольшим этапом каждый выполняет git fetch origin и читает актуальный STATUS другой ветки. Существующий npm run team:sync -- frontend/backend остаётся удобной командой для этого; она не делает merge.

В начале шага публиковать: текущая задача, занятые файлы, зависимости. После: что готово, проверки, ограничения, следующий шаг. Непрерывного фонового чтения GitHub нет; синхронизация происходит во время активной работы. Не ждать ручной пересылки отчётов через человека.

API и функционал больше не ждут разрешения дизайнера. Второй Codex обновляет контракт вместе с реализацией и публикует описание, чтобы шаблоны учитывали настоящие состояния. Продуктовые решения и участие пользователей продолжаются короткими этапами. Наличие кода/дизайн-витрины не означает готовность подключённых функций.

## Интеграция и публикация

1. Проверить git status и сохранить свою работу отдельным коммитом.
2. Получить origin, прочитать STATUS и diff коллеги.
3. Объединить проверенную ветку коллеги в свою, сохраняя общую историю. При конфликте разбирать обе версии; не применять ours/theirs ко всему проекту.
4. Выполнить npm test и проверку в браузере затронутого сценария. Серверные тесты используют временные базы, а не пользовательские данные.
5. Обновить собственный STATUS и отправить изменения обычным push в свою ветку.

Не использовать git add . вслепую. Секреты, .env, локальная база и личные файлы не публикуются. Чужую рабочую ветку не переписывать, force push не применять. Код отправляется в официальный origin; дополнительного репозитория не создавать.
