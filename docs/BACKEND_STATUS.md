## Готовые endpoints

| Endpoint | Готовое поведение |
| --- | --- |
| GET /api/state | Демо-состояние, серверные рейтинги, производные командные баллы, метаданные |
| GET /api/catalog | Открытые задачи, поиск/фильтры, сортировка по рейтингу и дате; доступны 0 и 20 баллов |
| POST /api/tasks | Сохранение исходной потребности как неопубликованного черновика |
| POST /api/ai/analyze | 3–6 уточняющих вопросов, сохранение введённых фактов; local или OpenAI с fallback |
| PUT /api/tasks/:id | Явное подтверждение полного снимка полей, версия, расчёт готовности |
| POST /api/tasks/:id/publish | Отдельная публикация подтверждённой карточки с названием, без минимального рейтинга |
| POST /api/tasks/:id/proposals | Отклик существующей команды на опубликованную задачу, 201 {proposal} |
| PATCH /api/proposals/:id | Ручное принятие/отказ владельцем задачи, 200 {proposal} |
| POST /api/proposals/:id/milestones | Принятый прототип +50, затем результат +100; 200 {proposal,team} |

Сервер раздаёт public/, сохраняет JSON атомарно и последовательно обрабатывает записи. После перезапуска сохраняются задачи, решения и история этапов. Демо-роль не является настоящей аутентификацией; GET /api/state включает неопубликованные задачи. Для каталога использовать GET /api/catalog.

## Новые операции для frontend

Отклик: POST /api/tasks/:id/proposals с {role:"team",teamId,idea,plan,duration,link}. Все четыре содержательных поля обязательны. Отправка и принятие дают 0 баллов. Низкий рейтинг, отсутствие прежних баллов и уже принятые другие команды не запрещают отклик. Повторный POST создаёт отдельный отклик: блокировать повторную отправку на время запроса, не повторять автоматически при неопределённом результате сети.

Решение: PATCH /api/proposals/:id с {role:"business",businessId,status:"accepted"|"rejected"}. Можно выбрать несколько команд или отклонить все; соседние отклики не меняются. До первого подтверждённого этапа решение можно пересмотреть. После этапа отказ возвращает 409; повторное принятие допустимо.

Подтверждение: POST /api/proposals/:id/milestones с {role:"business",businessId,key:"prototype"|"result",evidence}. Нужен принятый отклик и непустое описание того, что проверили. result допустим после prototype. Повтор key не добавляет баллы и не заменяет первое evidence. Использовать team.points из ответа; не прибавлять баллы на клиенте. Командные баллы не являются личным рейтингом студента.

Проверены полный путь с рейтингом задачи 0, несколько принятых команд, отказ всем, неверные роли/ID/поля/ссылки, сохранение без изменений после ошибок, конкурентные решения/этапы, повтор без начисления, перезапуск базы. Введённое evidence — описание проверки владельцем, не автоматическая проверка достоверности доказательств.

## AI: что действительно подключено

Серверный адаптер OpenAI Responses API готов. С ключом модель формулирует вопросы по конкретной задаче; поля карточки собирает сервер из слов человека. AI не подтверждает, не публикует, не оценивает готовность и не переписывает факты. Автоматическое извлечение всех полей из raw, оформление портфолио и оценка соответствия отклика пока не реализованы.

Без ключа работает local. При ошибке провайдера, отказе, неверном ответе или таймауте возвращается local с предупреждением о неуспешной внешней попытке. Ввод сохраняется; анализ не записывает базу. Показывать mode и warnings конкретного ответа. meta.aiMode говорит о настройке сервера, а не подтверждает успешный вызов.

Настройка только на сервере: OPENAI_API_KEY и OPENAI_MODEL (по умолчанию gpt-4.1-mini). Подготовлен локальный .env, исключённый из Git; ключ в чат не запрашиваем, содержимое не публикуем. CLI также принимает переменные окружения. Требуется ключ проекта с доступными API-кредитами; подписка ChatGPT сама по себе этого не подтверждает. После настройки нужен перезапуск и отдельная проверка живого вызова.

Ограничения: фиксированный адрес провайдера, 15 секунд, до 3000 выходных токенов и 64 КиБ ответа, строгая схема и дополнительная серверная проверка, отмена запроса, без автоматических повторов. Ключ и диагностика провайдера в HTTP-ответы не попадают. Промпт, настройка и официальные источники — src/ai/README.md и src/ai/openai.mjs. Локальные примеры — src/ai/examples.json. 10 новых тестов используют подставные ответы, не реальный аккаунт.

## Контракт и уточнения для его владельца

Схемы API v1 не изменены, обязательные серверные операции реализованы. Просьба обновить вводный абзац API_CONTRACT при следующей интеграции.

Уточнения реализации, которые стоит зафиксировать в контракте:

- idea/plan/evidence до 4000 символов, duration до 500, link до 2048, teamId до 160; строки обрезаются по краям. Ссылки — абсолютные HTTP(S), без логина/пароля, пробелов, управляющих символов и обратного слеша. Сервер ссылки не загружает.
- 409 означает также конфликт перехода: отказ после принятого этапа, этап до принятия отклика или result до prototype. Клиент показывает message и актуальное состояние, не повторяет автоматически.
- PUT передаёт полный fields: пропущенные ключи очищаются. Только confirmed === true. При 409 сохранить ввод и дать сравнить с актуальной карточкой.
- Подтверждённый черновик может быть пустым; опубликованная карточка должна сохранять непустой title. Это ранее сообщённое уточнение PUT, не новая схема.
- Первая публикация меняет version и publishedAt; повтор с актуальной version не меняет дату и сортировку. Нулевая готовность допустима.
- Непустой answers заменяет поле, пустой не стирает. Отсутствующий context получает raw дословно; явно пустой остаётся пустым. Эта семантика согласована frontend в 3600d55 и сохранена в remote.

## Следующий шаг frontend: конкретная передача

Выполни git fetch origin, прочитай этот статус из origin/feat/backend и объедини проверенные изменения. TASKER 1ca4a8a уже находится в общей истории backend; повторно переносить файлы вручную не нужно.

После принятия оформления пользователем работай короткими этапами:

1. Уточнение потребности: AI-вопросы → редактирование → явное подтверждение PUT → отдельная публикация. Успех только после ответа сервера, warnings видимы, при 409 ввод не теряется.
2. Отклик команды: идея/план/срок/ссылка → сохранение → список для бизнеса. Принятие нескольких, отказ и подтверждение этапов используют endpoints выше. Баллы брать с сервера.
3. Проверить в браузере полный путь от исходной боли до принятого результата, обновить FRONTEND_STATUS с проверками и открытыми вопросами.

На каждом этапе обсуждаем с участниками расположение основных действий и один практический выбор. Сейчас пользователь просит довести продукт до рабочего состояния; это не подтверждает конкретный визуальный макет. Незавершённые действия не изображать успешно выполненными.

## Новые функции пользователя: отдельное согласование модели

PRODUCT_QUALITY и STUDENT_CASES_PROPOSAL сохраняют все принятые решения: публичный каталог, один аккаунт и переключатель Студент/Бизнес, самостоятельное либо командное участие, профиль с материалами, личные кейсы, авторский вклад, отдельная отметка бизнеса, ограниченные бонусы и AI-соответствие 0–100 с объяснением (не вероятность успеха).

В v1 нет users/сессий, состава команд, solo-исполнителя, файлов, личных кейсов и личного ранга. Эти функции ещё не реализованы. Требуется согласовать расширение API с владельцем frontend; не выдавать демо-роль за вход и не подменять solo фиктивной командой. Историю хранит сервер, модель только предлагает текст. Точные бонусы/ранги, способ входа и публикация кейса предстоят совместному выбору.

Следующий независимый серверный шаг после синхронизации — конкретная схема личного аккаунта/исполнителя для согласования, затем реализация принятого расширения. При появлении ключа — живой AI smoke-test без личных данных. До интеграции мутаций в UI весь сайт нельзя считать завершённым.

## Обучение и организационные ограничения

Формат обучения: цель → одно практическое правило → короткое действие участника → наблюдаемый результат. Наш основной пример — заявки теряются в чатах. В карточке должны появиться конкретная боль, предоставленные примеры, ожидаемый результат и способ проверки; потери выручки и проценты нельзя выдумывать.

В прежней сверке документов осталось организационное расхождение: кейс описывает команду 3–5, общее положение 1–3. Пригодность команды из двух подтверждается организаторами. Работа ведётся в официальном GitHub; публикация кода сама по себе не означает сдачу заявки на платформе.
