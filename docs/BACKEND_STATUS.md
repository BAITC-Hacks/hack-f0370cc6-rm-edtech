## Реализовано

- `PUT /api/tasks/:id`: JSON `{role,businessId,version,industry,fields,confirmed:true}` → **200** `{task}`. Полный очищенный снимок; `confirmedFields` — только непустые поля, даты и version задаёт сервер. Официальный рейтинг пересчитывается в ответе; очищенное поле теряет баллы. Владелец и текущая версия проверяются внутри очереди записи; две правки одной версии не перезаписывают друг друга. Публикация и её дата сохраняются.
- `POST /api/ai/analyze`: JSON `{raw,industry,fields?,answers?}` → **200** `{mode:"local",fields,questions,missingFields,warnings}`. Только анализ, без обращения к store. Промпт, реализация, описание и два примера входа/выхода — `src/ai/`.
- `POST /api/tasks`: принимает JSON `{role:"business",businessId:"business_demo",raw,industry}`, возвращает **201** `{task}`. Raw — обязательная строка до 4000 символов, industry из meta.industries. Неизвестные поля запроса отклоняются, серверные id/dates/version/fields/confirmation/publication формируются сервером.
- `GET /api/state`: tasks с вычисленным rating, teams с вычисленными points, proposals, drafts, meta по общему контракту.
- `GET /api/catalog`: только published === true, rating по убыванию, publishedAt по возрастанию при равенстве. Параметры industry, level, query необязательны; пустые значения снимают фильтр. Слабые опубликованные задачи не скрываются.
- Раздача public/ с того же origin, правильные MIME для ES-модулей и CSS, HEAD для статики. При отсутствии index.html — технический текст, API остаётся доступным.
- JSON-хранилище по DATA_FILE, первый seed сохраняется на диск, записи последовательны через временный файл и rename. Повреждённая база не заменяется seed молча.
- Ошибки JSON `{error:{code,message,fields:{}}}`. Неверные/повторные параметры каталога и неверное JSON-тело — 400; неверная демо-роль/владелец — 403 FORBIDDEN; неизвестный маршрут/задача — 404 NOT_FOUND; неверный HTTP-метод реализованного endpoint — 405 с Allow; устаревшая версия — 409 CONFLICT; тело более 64 КиБ — 413. Внутренняя ошибка — 500 без стека в ответе.
- Выдача файлов ограничена public/, включая проверку реального пути и запрет dotfiles/Windows ADS.

## Исправления заготовок

- `cleanFields`: отклоняет null, массивы, скаляры, неизвестные ключи и значения не строкового типа. Пропущенные поля становятся пустыми строками; длины проверяются.
- Каталог строго различает опубликованную задачу и черновик. Query убирает крайние пробелы и ищет в тегах, как присланный preview frontend.
- `store.mutate()` возвращает отдельную копию результата, чтобы вызывающий код не мог менять сохранённое состояние без записи на диск.
- `src/state.mjs`: points не берутся из сохранённого team.points; рассчитываются по подтверждённым уникальным ключам этапов принятых предложений с подтверждением владельца задачи. Очки milestone берутся из STAGES, а не из произвольного persisted points. Это чтение существующих данных; HTTP-подтверждение этапов пока отсутствует.
- `src/seed.mjs` не менялся: все четыре набора содержат по пять примеров.

## Контракт и расхождения

- Схемы GET, POST /api/tasks, POST /api/ai/analyze и PUT /api/tasks/:id соответствуют docs/API_CONTRACT.md. При merge приняты редакционные уточнения владельца о поиске по тегам/trim, 400 и 405; backend новых ключей в общий контракт не вносил.
- Детали PUT для frontend: fields обязателен, отсутствующие ключи внутри него очищаются (полный снимок, не patch); version — положительное безопасное целое; только confirmed === true. При 409 оставить пользовательский ввод в форме, перечитать сохранённую задачу и предложить сравнение, не отправлять автоматически поверх чужой правки. Текст ошибки уже предлагает перечитать задачу.
- Граница обязательного title: черновик можно подтвердить пустым; у уже опубликованной задачи удаление title отклоняется 400, чтобы сохранить требование названия публичной карточки. Это уточнение поведения PUT, явно не описанное в исходном контракте; просим frontend подтвердить в STATUS и владельца внести его в текст контракта. Автоматического снятия с публикации нет.
- meta.aiMode='local' теперь соответствует работающему локальному анализатору. Это заглушка на правилах/шаблонах, не LLM. Для честной демонстрации обязательны предупреждения из ответа; внешний API не вызывался.
- Raw/industry обязательны, fields/answers необязательны. MissingFields считается по всем пустым полям, включая title. Непустой answers имеет приоритет над fields; пустой ответ не стирает поле. Явно пустой context отличается от отсутствующего. Frontend подтвердил эту семантику в 3600d55, схема не изменена.
- При неверном результате генератора/ошибке/таймауте возвращается 200 с безопасным локальным ответом и дополнительным warning. Неверный пользовательский ввод остаётся 400. Валидатор фактов намеренно консервативен для текущего локального режима; это не универсальная проверка смысловой достоверности будущей модели.
- /api/state по контракту включает неопубликованные задачи для демонстрационной роли; каталог должен использовать /api/catalog. Это не production-разграничение доступа.
- Из frontend приняты preview/team:sync scripts и .gitignore для `.env.*`, `.env.example`, `data/*.json.tmp`. Backend самостоятельно корневые настройки не менял; ignore не очищает историю Git.

## Подключение подтверждения для frontend

```http
PUT /api/tasks/<id из POST или GET>
Content-Type: application/json

{"role":"business","businessId":"business_demo","version":1,"industry":"Услуги","fields":{"title":"Не терять заявки из чатов","data":"Обезличенные примеры обращений предоставит владелец"},"confirmed":true}
```

Только после явного действия человека; в реальном UI отправить полный текущий fields, а не только изменённые ключи. Ответ 200 — task с новым version, confirmedAt, confirmedFields и rating.score=20 для этого примера; по-прежнему published=false. Удаление data с сохранением только title даёт 0. Отображать значения из ответа, не повышать рейтинг по факту получения AI-предложения. После 409 ввод пользователя должен оставаться доступным для сравнения. Кнопка публикации пока не имеет работающего endpoint.

## Подключение анализа для frontend

```http
POST /api/ai/analyze
Content-Type: application/json

{"raw":"Заявки клиентов теряются в чатах","industry":"Услуги","fields":{},"answers":{}}
```

Отобразить questions и редактируемые fields; при следующем проходе отправить изменённые fields и новые answers. Не добавлять taskId/role/confirmed/rating в этот запрос: они не предусмотрены схемой анализа. Ввод остаётся на клиенте до отдельного сохранения. Warnings показывать пользователю, особенно сообщение о заглушке или восстановлении после ошибочного результата. В src/ai/examples.json есть оба прохода; src/ai/prompt.mjs — промпт для демонстрации; src/ai/README.md — объяснение правил и ошибок. UI этого этапа backend не реализовывал.

## Запрос для первого шага конструктора

```http
POST /api/tasks
Content-Type: application/json

{"role":"business","businessId":"business_demo","raw":"Заявки клиентов теряются в чатах","industry":"Услуги"}
```

Ответ 201: `{task}` с id, raw, industry, company="Мой бизнес", пустыми fields, confirmedFields=[], confirmedAt=null, published=false, publishedAt=null, version=1, серверными createdAt/updatedAt и rating.score=0. После успешного ответа использовать возвращённый task, не рассчитывать рейтинг на клиенте. Это демо-идентификация, а не аутентификация. Повторная отправка POST создаёт новый черновик: UI должен блокировать кнопку на время запроса и не повторять POST автоматически при неопределённом результате сети.
