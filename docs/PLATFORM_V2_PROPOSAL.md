# Три страницы и API v2 — конкретное предложение для frontend

Статус: новое ТЗ пользователя от 23.09.2026. Это предложение расширения для согласования, НЕ изменение действующего API_CONTRACT и НЕ отчёт о подключённых маршрутах. Первый короткий шаг backend — внутренние сервисы аккаунтов, профилей, заказов и файлов с тестами; подключение HTTP после ответа владельца контракта.

## Принято пользователем

Три основные страницы: Главная, Заказы, Профиль. Общая шапка и видимый переключатель Студент / Владелец бизнеса; один аккаунт сохраняет данные обеих ролей. Вход через Google (email/пароль отклонён). Каталог доступен гостям, вход нужен для отклика и размещения. Оплата напрямую между сторонами; платформа хранит результат и отзыв, не принимает платежи.

Главная — презентация, два понятных пошаговых сценария, преимущества и переход к входу/регистрации. Поиск, каталог и форма публикации находятся на странице Заказы. CTA и навигация допустимы на главной; обработку заказов туда не переносим.

Заказы студента: категории Образование, Ритейл, Логистика, Туризм, Услуги, Другое; открытые заказы с описанием, категорией, статусом и датой. Полный заказ и отклик — внутри страницы (панель/диалог), без четвёртого основного раздела. Заказы бизнеса: вкладки «Опубликовать проблему» и «Мои проблемы». Профиль: имя, контакты, фото, навыки/портфолио и компания/сфера. Смена роли сохраняет обе части профиля.

Пользователь просит «в стиле HH.ru». Предлагаю взять знакомую структуру поиска, карточек и личного кабинета; точное сочетание с текущей айдентикой TASKER должен обсудить frontend с участником, не считать его уже утверждённым. Лэндинг не должен обещать безопасную сделку, подтверждённую выплату или гарантию трудоустройства.

## Модель, отдельно от demo v1

Приватная база schemaVersion=2: users, sessions, orders, applications, files, reviews. Файл отдельно от data/state.json. GET /api/state v1 никогда не получает эти коллекции. Старые демонстрационные задачи/команды не превращаются автоматически в личные аккаунты и не удаляются.

User (внутри сервера): id, googleSubject, email, emailVerified, name, contacts, photoUrl, activeRole, student:{skills,portfolio}, business:{companyName,industry}, version, createdAt, updatedAt. Один googleSubject — один пользователь. Смена email не создаёт дубль; один email не объединяет разные Google-идентичности. Пароли не собираются.

Собственный профиль исключает googleSubject и любые сессионные данные. Публичный профиль: только id,name,photoUrl,student,business. Контакты и email не выдаются в каталоге/откликах автоматически. Портфолио первого шага — редактируемые ссылки {title,url,description}, без ложной отметки бизнеса; полноценные кейсы и их версии остаются следующим этапом STUDENT_CASES_PROPOSAL.

Session: tokenHash,userId,createdAt,expiresAt. Случайный токен возвращается только в HttpOnly cookie; в базе только хеш. Активная роль читается из пользователя на сервере, а не из body role. Права на заказ проверяются по ownerId, права на отклик — по studentId.

Order: id,ownerId,title,category,description,status,version,attachments:[fileId],createdAt,publishedAt,updatedAt,history. Четыре статуса: open / in_progress / completed / closed («Открыт», «В работе», «Выполнен», «Закрыт»). Название до 160, описание до 4000; category из прежнего списка INDUSTRIES. Старый rating готовности и новый рабочий status — разные вещи. Перенос AI-уточнения и рейтинга в v2 согласовать отдельно, их не удалять из обязательного демо v1.

Application: id,orderId,studentId,message,status,createdAt. Самостоятельный отклик по личному user.id; фиктивная команда не создаётся. Предыдущий запрос пользователя на команды сохраняется в backlog; v1 командный путь остаётся рабочим. Членство реальных пользователей в командах — отдельное расширение, а не team.members-число.

## Предлагаемые HTTP endpoints

Все JSON-ошибки сохраняют форму v1 {error:{code,message,fields:{}}}; дополнительно 401 (нужен вход), 429 (ограничение запросов), 503 (Google не настроен), 502 (провайдер недоступен). Маршруты ниже ещё НЕ подключены.

| Метод и путь | Вход | Ответ / доступ |
| --- | --- | --- |
| GET /api/v2/auth/google/start | role=student/business, returnTo — внутренний маршрут | 302 Google + временная browser-bound cookie |
| GET /api/v2/auth/google/callback | code,state от Google | Проверка state/cookie, 303 назад + новая session cookie |
| GET /api/v2/session | — | {user:null} гостю либо {user:OwnProfile,csrfToken}; никогда sessionToken |
| POST /api/v2/auth/logout | {} | {ok:true}, отзыв сессии, удаление cookie |
| GET /api/v2/profile | — | {user:OwnProfile}, нужен вход |
| PATCH /api/v2/profile | version и изменяемые поля профиля | {user}, только свой; 409 при старой версии |
| GET /api/v2/profiles/:id | — | {profile:PublicProfile}, без контактов/email |
| GET /api/v2/orders | category?,query? | {orders:PublicOrder[]}; гостю тоже, только open, новые первыми |
| GET /api/v2/orders/mine | — | {orders:OwnOrder[]}, бизнес, только ownerId, все статусы |
| POST /api/v2/orders | {title,category,description} | 201 {order}, бизнес; публикация open после явного действия |
| GET /api/v2/orders/:id | — | {order:PublicOrder}, без приватной истории, контактов и текстов откликов |
| PATCH /api/v2/orders/:id/status | {version,status,evidence?} | {order}, владелец, контролируемый переход |
| POST /api/v2/orders/:id/applications | {message} | 201 {application}, студент, только open, не свой заказ |
| GET /api/v2/orders/:id/applications | — | {applications}; владелец видит все, студент только свои |
| PATCH /api/v2/applications/:id | {version,status:accepted/rejected} | {application,order}, владелец; version заказа |
| POST /api/v2/orders/:id/files | raw bytes; Content-Type, X-File-Name (encodeURIComponent), X-Order-Version | 201 {file,orderVersion}, владелец open |
| GET /api/v2/files/:id | — | attachment download; авторизованный доступ по правилам ниже |
| DELETE /api/v2/files/:id | {version} | {deletedId,orderVersion}, владелец open |
| POST /api/v2/orders/:id/reviews | {studentId,text} | 201 {review}, владелец после принятого результата |
| GET /api/v2/profiles/:id/reviews | — | {reviews}, публичные отзывы о выполненных работах |

PATCH профиля сохраняет отсутствующие ключи. Вложенные student/business тоже patch, а переданные skills/portfolio полностью заменяют соответствующий список. Клиент не может менять id,email,emailVerified,googleSubject,createdAt или приписывать подтверждение/баллы. Ограничения: контакты 500, навыки до 30 строк по 80, портфолио до 20 ссылок с описанием до 2000. Фото сейчас URL; загрузка собственного изображения требует отдельного шага обработки изображений.

При HTTP-интеграции: same-origin cookie HttpOnly; SameSite=Lax; Secure на HTTPS, локальный HTTP только loopback. OAuth state отдельный от session и одноразовый, 10 минут. Сессия 7 дней. На мутации — проверка точного разрешённого Origin и CSRF; вход — ограничение частоты. Секреты/токены не отправляются в URL приложения или JSON, не пишутся в логи. Прямой callback из Google — исключение по Origin, защищается state+cookie+PKCE.

## Переходы и решения для согласования

- Создание после явной публикации даёт open. Список открытых не прячет новичков и не требует баллов.
- Принятие первого отклика: open → in_progress. Можно принять дополнительных исполнителей из уже поданных откликов. Новые отклики после начала работы пока не принимаются.
- До завершения можно пересмотреть выбор. Если отклонён последний принятый исполнитель: in_progress → open с записью в истории, прежний publishedAt сохраняется.
- Один активный pending/accepted отклик на человека и заказ; после rejected разрешена новая попытка. Это новое предложение для личных откликов, v1 не меняется.
- Выполнен: in_progress → completed только владелец с описанием принятого результата. Выбор исполнителя сам по себе не означает выполненную работу или оплату.
- Закрыт: open → closed либо in_progress → closed с причиной; completed → closed как архивирование. Закрытие незавершённого не выдаёт его за успешный кейс. Обратные переходы из completed/closed запрещены в первом шаге.
- status=completed не подтверждает оплату. Отзыв пишет владелец о выбранном исполнителе после completed; для closed должна сохраниться запись принятого результата. Один отзыв на заказ/исполнителя, до 2000 символов, без самостоятельного отзыва о себе. Публичный отзыв хранит написанный для публикации text, название заказа и дату принятия результата; приватное evidence не копируется в публикацию. Звёзды, личные баллы и редактирование отзыва пока не добавляем.
- Все изменения версии/состояния последовательны: две операции со старой version не могут обе пройти.

## Файлы первого шага

ТЗ: PDF или UTF-8 TXT, до 5 МиБ/файл, до 3 приложений/заказ, до 20 МиБ на аккаунт. Название без путей/управляющих символов, MIME/расширение/сигнатура согласованы. DOCX, фото и файлы отклика/резюме — расширение после согласования; не показывать их загрузку как готовую.

Содержимое хранится в отдельной приватной базе как base64 (ограниченный локальный MVP), а не public/. Метаданные выдаются белым списком, без blob. Удаление/прикрепление меняют version заказа и разрешены владельцу, пока open. Владелец читает свои файлы; вошедший студент читает ТЗ открытого заказа. После начала работы доступ остаётся владельцу и принятым исполнителям. Переключение роли не передаёт чужие права.

HTTP выдаёт Content-Disposition: attachment и nosniff; HTML/SVG/исполняемые файлы не разрешены. Проверка формата не заменяет антивирус: сканирование и отдельное объектное хранилище нужны перед публичной эксплуатацией с реальными документами.

## Что нужно от первого Codex

Прочитай новое ТЗ и ответь в FRONTEND_STATUS, принимаешь ли пути/схемы и переходы выше. Особенно: отдельные v2 orders, правила статусов, solo-состав отклика, формат загрузки raw bytes вместо multipart и профиль patch. Имя файла передаётся encodeURIComponent(file.name) в X-File-Name, текущая версия заказа — десятичной строкой в X-Order-Version; сервер декодирует один раз. После согласования обновляем общий API_CONTRACT и подключаем HTTP/интерфейс короткими проверяемыми шагами. Новые страницы не должны отправлять demo role/businessId вместо настоящей сессии.

Не требуется ручная пересылка через участников: предложение и результат публикуются в feat/backend. Backend продолжает внутренние сервисы и тесты, не меняя public/** и действующий контракт в одиночку.

## Проверка с участниками

На каждом этапе показываем один законченный сценарий и обсуждаем одно решение по интерфейсу. Практика: студент после Google-входа открывает тот же заказ, пишет своё предложение и видит сохранённый отклик; бизнес выбирает его и видит «В работе». При смене роли данные не исчезают. Отдельно проверяем, что второй аккаунт не может изменить чужой заказ и что неизвестный AI процент не становится подтверждённой потерей выручки.

## Основания для подключения

- [Google: серверный OAuth, регистрация клиента и redirect URI](https://developers.google.com/identity/protocols/oauth2/web-server)
- [OWASP: управление сессиями](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- [OWASP: загрузка файлов](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

Для настоящего входа нужны OAuth Client ID, Client Secret и зарегистрированный callback у Google. Серверный адаптер и подставные тесты не доказывают, что внешний вход уже работает. Google Client Secret хранится локально/в окружении, не в чате или Git. Настраивать окончательный callback после согласования маршрутов. Пользователь выбрал отложить настройку Google: консоль была открыта на первом согласии с условиями, условия не принимались, OAuth-клиент не создавался. Не повторять настройку до его возобновления.
